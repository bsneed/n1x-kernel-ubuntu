# Review: n1x-kernel-ubuntu, initial snapshot

## Summary

The repository builds Omarchy's `linux-omarchy-aarch64` 7.3 kernel recipe as Ubuntu 26.04
arm64 packages. It also ships NVIDIA 620.73.04 open modules as a DKMS package with Omarchy's
N1x patches and a GB20B suspend fix, plus root-run install, default and remove scripts. The
build side is solid: every download is pinned and checked, the Omarchy patch order comes from
the pinned PKGBUILD, and config drift fails the build. The pure GRUB/cmdline helpers are
carefully written and well tested. The riskiest code is the part with no tests:
`install.sh`'s package selection and restore logic.

The most important findings:

- **F1:** `install.sh` removes NVIDIA packages that have nothing to do with the driver branch
  (`nvidia-settings`, `nvidia-prime`, `nvidia-container-toolkit`, `libnvidia-container1`).
- **F2:** `nvidia-dkms.sh` applies patches with `patch --batch`, which silently *reverts* any
  patch that upstream has already merged, and exits 0.
- **F3:** The "boot once, fall back" safety net assumes `GRUB_DEFAULT=saved` but never checks
  it.
- **F4:** Install, remove and the apt pin depend on exact Ubuntu package revisions, which the
  archive will drop.

21 findings: 0 Critical, 5 Major, 13 Minor, 3 Nit.

## Findings

### F1 — Major — install.sh removes unrelated NVIDIA packages

- **Location:** `scripts/install.sh:50-54`, `scripts/install.sh:137-139`.
- **Violated requirement:** README step 2 says the script removes "the other NVIDIA branch's
  packages, e.g. 615 and the prebuilt `linux-modules-nvidia-615-open-*`".
- **What happens:**
  - `nvidia_installed` selects every installed `^(lib)?nvidia-…` package except a short
    exclusion list.
  - The loop then removes every one that isn't `*-620` or `*-620-*`.
  - So branchless packages are removed: `nvidia-settings`, `nvidia-prime`,
    `nvidia-container-toolkit`, `nvidia-container-toolkit-base`, `libnvidia-container1`,
    `libnvidia-container-tools`, `nvidia-cuda-toolkit`, `nvidia-modprobe`, and so on.
  - apt also removes whatever depends on them.
- **Evidence (reproduced):** the probe output was
  `nvidia-settings- nvidia-prime- nvidia-container-toolkit- libnvidia-container1-`, along
  with the 615 packages. Ubuntu's `nvidia-driver-615-open` Recommends `nvidia-settings` and
  `nvidia-prime`, so a stock install has both.
- **Failure scenario:** a P16 user runs Docker with GPU access, or has the default
  ubuntu-drivers install. `sudo bash scripts/install.sh` silently uninstalls the container
  toolkit and the settings/prime tools. `--remove` only restores them if those exact versions
  are still downloadable (F4).
- **Fix:** select only branch-versioned packages to replace. That means names matching
  `-[0-9]{3}(-open|-server)?$`, `^nvidia-firmware-[0-9]{3}-`, or `^linux-modules-nvidia-[0-9]{3}-`
  where the number isn't `$BRANCH`. Put the selection in a pure function in lib.sh, with tests
  that cover nvidia-settings, nvidia-prime, the container toolkit and 615/620 names.

### F2 — Major — `patch --batch` silently reverts already-applied NVIDIA patches

- **Location:** `scripts/nvidia-dkms.sh:44`.
- **Violated requirement:** focus 2, "anything that could silently build the wrong thing".
  It also contradicts docs/nvidia-gb20b-suspend.md:67-74, which expects a merged patch to make
  the build fail.
- **What happens:** GNU patch's `--batch` (`-t`) assumes reversed patches when they look
  reversed. A patch whose change is already in the tree is applied *in reverse* and exits 0.
- **Evidence (reproduced, GNU patch 2.7.6):** `--batch` printed "Assuming -R.", exited 0, and
  left the file reverted. `-N`/`--forward` exited 1.
- **Failure scenario:** `NVIDIA_VERSION` is bumped to a release in which NVIDIA has merged
  0008 (its header says it is meant for main) or dropped GB20B from the list. The build
  undoes NVIDIA's fix and ships it, with no error. The kernel side at build.sh:99 and :106
  uses `-N`, which is safe. Omarchy's PKGBUILD uses `--batch` too, so the hazard is inherited,
  not introduced.
- **Fix:** use `patch -d "$TREE" -p1 --forward --batch --fuzz=0 --quiet`, or run
  `git apply --check` first. Add a test that applies a patch twice and expects failure.

### F3 — Major — the fallback boot depends on `GRUB_DEFAULT=saved`, which is never checked

- **Location:** `scripts/install.sh:149-151`, `:158-161`, `:195`. README lines 159-160 and 141.
- **Violated requirement:** README says it "keeps the running kernel as GRUB's default and
  boots the new one once… a hang… falls back to the old kernel". `--default` claims to make
  the new kernel the default.
- **What happens:** `grub-set-default` only has an effect with `GRUB_DEFAULT=saved`.
  - Stock Ubuntu ships `GRUB_DEFAULT=0`. proart-p16-linux's `install/01-kernel.sh:54` sets
    `saved`, which is why rtx24 works.
  - With `GRUB_DEFAULT=0`, entry 0 boots the newest kernel by version sort, which is 7.3.0-n1x1.
  - So after one boot (good or bad) the untested kernel stays the default, and `--default` is
    a no-op that reports success.
  - The README says other N1x laptops "should work", and those won't necessarily have
    proart-p16-linux.
- **Evidence:** inspection, plus the GRUB 00_header semantics. Not reproduced on a GRUB
  install.
- **Failure scenario:** a Zenbook A16 user with stock GRUB installs the package, and the 7.3
  kernel hangs on the dock. Every later boot also goes to 7.3, until they pick the old kernel
  by hand from "Advanced options".
- **Fix:** in `do_install`, read `GRUB_DEFAULT`.
  - If it isn't `saved`, either set it (recording the old value in `$STATE` and restoring it
    on `--remove`) or die with instructions.
  - Make `do_default` fail the same way.
  - Add a test for the `GRUB_DEFAULT` get/set helper.

### F4 — Major — exact Ubuntu revisions make install, remove and updates brittle

- **Location:**
  - `scripts/install.sh:121-131` (pin on `$NVIDIA_UBUNTU_VERSION`);
  - `:140` (`want` is `pkg=620.73.04-0ubuntu0.26.04.1`);
  - `:170-180` (pin deleted, then `apt install` of the exact versions in `nvidia-before`);
  - `nvidia-dkms/control:8` (`nvidia-kernel-common-620 (= …0ubuntu0.26.04.1)`).
- **Violated requirements:** README "Remove" says it "reinstalls the NVIDIA packages that were
  there before (exact versions)". README "Updates" promises the pin keeps userspace and modules
  matched.
- **Failure scenarios:**
  1. **Fresh install.** Ubuntu respins 620 (`…26.04.2`) in -proposed or -updates, and Launchpad
     drops `.1` from the pocket index. `apt-get install nvidia-utils-620=…26.04.1` then fails
     with "Version not found". This happens only after the state dir and the pin have been
     written.
  2. **Remove.** 615 gets a security respin (`615.71.09-0ubuntu0.26.04.3`; NVIDIA publishes
     security bulletins often). `nvidia-before` names `.2`, which is gone from -updates and
     -security, so `--remove` dies at line 180.
     - Line 170 has already deleted the pin, and the EXIT trap removes the proposed source.
     - The system keeps 620 with no pin, so a later `apt full-upgrade` can move
       `nvidia-kernel-common-620` and remove our DKMS package to satisfy it.
  3. **Security updates.** The pin at 1001 on an exact Ubuntu revision also blocks Ubuntu's
     security respins of the same upstream 620.73.04. The README does not mention this.
- **What still works:** the module/userspace match does hold across the move from -proposed
  to -updates, because the version string is unchanged. The README is right about that.
- **Fix:**
  - Pin on the upstream version: `Pin: version 620.73.04-*`. In control, use
    `nvidia-kernel-common-620 (>= 620.73.04), nvidia-kernel-common-620 (<< 620.73.05)`, as
    Ubuntu's own `nvidia-driver-620-open` does.
  - In `do_install` and `do_remove`, run `apt-get install --simulate …` (or
    `apt-cache madison` per package) before changing anything, and die with a clear message
    if a version is missing.
  - In `do_remove`, keep the pin until the restore transaction succeeds.
  - In the README, state that userspace security updates wait for a rebuild.

### F5 — Major — a failed DKMS build for the default (Ubuntu) kernel only warns

- **Location:** `scripts/install.sh:87-90`.
- **Violated requirement:** README step 2 says modules are built for every kernel with headers,
  "Ubuntu's `linux-nvidia` included, so the fallback kernel keeps a GPU driver". Line 150
  keeps that kernel as GRUB's default.
- **What happens:** the same apt transaction has already removed the prebuilt
  `linux-modules-nvidia-615-open-7.0.0-*`. If the 620 build fails for the previous kernel, the
  script warns, carries on, and prints "Done".
  - The N1x has no other display engine, so the default kernel comes up with only
    efifb/simpledrm and no GPU.
- **Failure scenario:** a later linux-nvidia ABI (e.g. 7.0.0-1030) changes the dma-buf
  backport, so `PATCH_MATCH ^7\.0\.0-` applies a patch that no longer fits, or conftest breaks.
  This is a realistic trigger.
- **Fix:** treat `$(cat "$STATE/previous-kernel")` like `$RELEASE`, and die. Better still,
  check that the build will work before removing the 615 modules (build first, then switch).
  At minimum, make the final message report the kernels without a driver.

### F6 — Minor — `--remove` cannot restore a user's own `pci=` options; `grub.before` is unused

- **Location:** `scripts/grub.sh:12-28`, `:31-42`; `scripts/install.sh:117`, `:183`, `:196`.
- **What happens:** `_pci_merge` replaces a same-named option with a different value, and
  `_pci_unmerge` drops every option equal to ours. `--remove` therefore can't tell ours from
  the user's.
  - `$STATE/grub.before` is saved at :117 and deleted at :196 without ever being read.
- **Evidence (reproduced):**
  - `pci=hpmmioprefsize=64G` → install → `32G` → remove → option gone.
  - `pci=hpbussize=0x80` (already present, e.g. from Omarchy's own instructions) → remove →
    gone.
- **Fix:** record the original `pci=` value (or the whole original
  `GRUB_CMDLINE_LINUX_DEFAULT`) in `$STATE`. On remove, restore that value when the current
  line still equals what install wrote, and otherwise undo only the options that were added
  or changed. Add tests for both cases.

### F7 — Minor — modules built by `dkms_all_kernels` never reach the initramfs

- **Location:** `scripts/install.sh:78-92`, `nvidia-dkms/postinst:5-11`.
- **What happens:**
  - The postinst refreshes every initramfs, but `common.postinst` builds only for the
    current and newest kernels (verified in dkms 3.2.2-1ubuntu1).
  - dkms 3.x never rebuilds an initramfs: `REMAKE_INITRD` is deprecated, verified in
    `/usr/sbin/dkms`.
  - Kernels that `dkms_all_kernels` builds afterwards keep an initramfs without the new
    nvidia.ko. Because nvidia.ko is missing rather than stale, that is the benign case.
- **The stale case (plausible):** dpkg runs our postinst's `update-initramfs` before it
  removes `linux-modules-nvidia-615-open-<k>`. That kernel's initramfs then keeps 615's
  nvidia.ko next to 620 userspace. The ordering inside the apt transaction is not controlled.
- **Health check:** check.sh:70-71 then reports FAIL for that kernel.
- **Fix:** after `dkms_all_kernels`, run `update-initramfs -u -k all` once (or per kernel
  built) as the last package step of `do_install`. Do the same at the end of `do_remove`'s
  apt step.

### F8 — Minor — `grub_default_get` misses indented, `export`ed or grub.d assignments

- **Location:** `scripts/grub.sh:96-121`.
- **What happens:** both get and set match only `^GRUB_CMDLINE_LINUX_DEFAULT=`.
- **Evidence (reproduced):** an indented line reads as empty, and `grub_default_set` appends
  a second line, `GRUB_CMDLINE_LINUX_DEFAULT="pci=…"`. That line wins when grub-mkconfig
  sources the file, so `quiet splash` and `acpi_osi` disappear from the boot.
- **Related:** values set in `/etc/default/grub.d/*.cfg` are sourced after
  `/etc/default/grub` and override the edit. The `pci=` options are then silently absent,
  which check.sh only catches after a reboot.
- **Fix:**
  - Make get fail on any `GRUB_CMDLINE_LINUX_DEFAULT` occurrence that isn't a plain
    assignment (grep `-E '^[[:space:]]*(export[[:space:]]+)?GRUB_CMDLINE_LINUX_DEFAULT='`).
  - Die if any `/etc/default/grub.d/*.cfg` sets the variable.
  - After `update-grub`, check that `grub.cfg`'s linux line for `$RELEASE` contains the
    options.
  - Add tests for each case.

### F9 — Minor — `grub_entry_id` requires a submenu

- **Location:** `scripts/grub.sh:135`; `scripts/install.sh:73`.
- **What happens:** with `GRUB_DISABLE_SUBMENU=y` the entries are top level, `sub_id` is
  empty, and the function fails (reproduced: rc=1).
- **Failure scenario:** `do_install` dies at :150. That is after the packages, the pin and
  the cmdline are all in place, but before `grub-reboot`, so the install ends half done with
  an error.
- **Fix:** print just the entry id when there's no enclosing submenu (track the brace depth,
  or reset `sub_id` at a top-level `}`). Add the flat layout to the tests.

### F10 — Minor — re-running install resets a chosen default

- **Location:** `scripts/install.sh:150`.
- **What happens:** after `--default`, running `install.sh` again (for example to pick up a
  new DKMS revision) sets the default back to the Ubuntu kernel. Nothing in the output says
  that the earlier choice was undone.
- **Fix:** when `uname -r` is already an n1x release and `saved_entry` points at it, keep it.
  Otherwise, say in the final message that the default was reset.

### F11 — Minor — rebuilds without a revision bump are not reinstalled; dkms .deb choice is loose

- **Location:** `scripts/install.sh:102-104`, `:142`.
- **What happens:**
  - apt treats a local .deb with an installed version as already installed. A rebuilt kernel
    or DKMS package with an unchanged `N1X_REVISION` or `NVIDIA_N1X_REVISION` (e.g. a config
    or patch edit) is silently not installed. The README documents the bump, but nothing
    enforces it.
  - The dkms glob `${NV_DKMS}_$NVIDIA_VERSION-*.deb | head -1` would pick `n1x1` over
    `n1x2` in a directory that holds both.
- **Fix:**
  - Use the exact filename `${NV_DKMS}_${NVIDIA_VERSION}-n1x${NVIDIA_N1X_REVISION}_arm64.deb`.
  - Compare the installed package's md5sums or control hash with the .deb, and die
    ("raise the revision"), or pass `--reinstall` deliberately.

### F12 — Minor — build.sh doesn't cross-check `sources` against the pinned PKGBUILD

- **Location:** `scripts/build.sh:60-62`, `:81-88`.
- **What happens:** `KERNEL_VERSION`, `KERNEL_URL` and `KERNEL_SHA256` are independent of
  the PKGBUILD's `pkgver`, `source` and `sha256sums`, and `_rcpatch` is ignored.
  - Today they agree. I verified that pkgver is 7.3, `_rcpatch` is unset, and the tarball
    SHA-256 is equal.
- **Failure scenario:** Omarchy moves to a `7.4rc3` recipe. Its prepare() applies
  `patch-7.4-rc3` on top of `linux-7.3`, but build.sh would apply the 7.4 patches straight to
  7.3, or to whatever `sources` names. Fuzz=0 probably catches that, but not necessarily.
- **Fix:** in the PKGBUILD subshell, also print pkgver, `_rcpatch` and the tarball sha256.
  Die unless pkgver equals `KERNEL_VERSION`, `_rcpatch` is empty, and the sha matches
  `KERNEL_SHA256`.

### F13 — Minor (plausible) — 0010 is scoped to the GB20B chip, not to N1x devices

- **Location:**
  `patches/nvidia/0010-let-the-n1x-gpu-go-through-system-suspend-again.patch:36-37`;
  `docs/nvidia-gb20b-suspend.md:24`, `:47`.
- **What I verified:** the patch is minimal. It changes the only assignment of
  `is_pm_unsupported` (dynamic-power.c:3201), which is read only by `nv_suspend_devices` and
  `nvidia_suspend` (nv.c:4850, nv.c:5057). GB20C keeps 620's behaviour.
- **The scope gap:** GB20B also appears to be DGX Spark's GB10.
  - The names table lists `0x2E12 "NVIDIA GB10"` among the N1x IDs.
  - spark1 is 10de:2e12.
  - The patch comment itself says GB20B is "*also*" the N1x GPU.
  - NVIDIA added GB20B and GB20C to the list together, which suggests the target was GB10.
  - Not confirmed: that needs PMC_BOOT_42 on spark1.
- **Failure scenario:** the DKMS package is installed on a DGX Spark (install.sh only warns
  on non-H7607BA). It re-enables a suspend path NVIDIA meant to disable there.
- **Fix:** either scope the check by PCI device ID
  (`nv->pci_info.device_id` ∈ {0x2E03, 0x2E06, 0x2E13}), or state in the doc and README that
  the patch applies to every GB20B part, GB10 included. Make install.sh die, not warn, on
  non-N1x GPUs.
- **Doc evidence check:** the doc's evidence holds up against the source.
  - 615's list (g_gpu_nvoc.c:481-484) is exactly the six chips the doc names.
  - "This is the only place the flag is set" is true.
- **Doc evidence, wording:**
  - 4/4 cycles on one machine is a small sample. Say so in the draft report.
  - "615 suspends and resumes on these laptops" rests on Omarchy and on Ubuntu 7.0 + 615.71.09,
    not on 615 on 7.3. Name which one.

### F14 — Minor — no Secure Boot preflight or caveat

- **Location:** `scripts/install.sh:94-107`; README "Install".
- **What happens:** the kernel is signed with a throwaway build key
  (`config/n1x.config:16-17`) and isn't shim-signed. With Secure Boot on, GRUB/shim refuses to
  load it ("bad shim signature").
  - With F3 that can loop.
  - TODO.md lists MOK signing as optional, and the README never says Secure Boot must be off.
- **Fix:** run `mokutil --sb-state`, and die (or warn loudly) when Secure Boot is enabled.
  Add a README line.

### F15 — Minor — check.sh health checks rely on heuristics or false positives

- **Location:** `scripts/check.sh:28-29`, `:66-73`, `:77`.
- **Initramfs freshness (:66-73):** mtime comparisons don't prove the loaded module is the
  installed one. The authoritative check recorded in project memory compares
  `/sys/module/nvidia/srcversion` with `modinfo -F srcversion nvidia`.

## What's Done Well

- **Downloads are pinned and verified:**
  - every download is pinned and SHA-256-checked, and the check runs on every build, not
    just the first download;
  - the base config is checked twice (.deb, then the extracted file);
  - the Omarchy pin is verified by commit, with no local changes allowed.
- **The patch list comes from the pinned PKGBUILD**, using the same expansion as its
  `prepare()`. I verified the result: 579 patches, in order.
- **`config-check.sh` guards the config.** It turns Kconfig's silent drops into build
  failures, and its tests cover the negative cases.
- **The cmdline editing is careful:** it splits on single spaces, so `acpi_osi=\"!Windows 2022\"`
  survives the round trip byte for byte. It is idempotent, ignores look-alike parameters, and
  rejects unsupported quoting instead of guessing.
- **`grub_default_set` writes atomically.** It writes a temp file and `mv`s it into place,
  keeps the permissions, and passes the value through `ENVIRON`, so awk never interprets it.

  `nvidia-dkms-620-open`, so Ubuntu's metapackages are satisfied. The `Pin-Priority: -1` on
  Ubuntu's DKMS package is correct, and the initramfs refresh in postinst and postrm fixes the
  real stale-module bug.
- **The test build against the new kernel tree** catches a kernel API break before install.
  The release check at build.sh:130 guards against a LOCALVERSION surprise.
- **The suspend doc is evidence-based:** it shows exact source locations, a before/after
  failure count, and a clear rule for dropping the patch. Rebase notes in 0005, 0007 and 0009
